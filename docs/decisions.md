# Architecture Decision Records

## ADR-001: Монорепо с pnpm workspaces

**Дата:** 2026-10-05  
**Статус:** Принято

**Контекст:**  
Нужно организовать frontend, backend и общие типы в одном репозитории.

**Решение:**  
pnpm workspaces: `apps/frontend`, `apps/backend`, `packages/shared`.

**Причины:**  
- Единый репозиторий для небольшой команды (семейный проект)
- Общие типы без дублирования
- Простая настройка без Lerna/Turborepo

## ADR-002: Domain Layer как чистые функции

**Дата:** 2026-10-05  
**Статус:** Принято

**Контекст:**  
Бизнес-логика генерации меню и Shopping List — главная ценность приложения. Её нужно тестировать надёжно.

**Решение:**  
`menuGenerator`, `shoppingListBuilder`, `ingredientScaler` — чистые функции без зависимостей от Prisma, HTTP и React.

**Причины:**  
- Детерминированные тесты
- Возможность передавать `random` как параметр
- Изоляция от инфраструктуры

## ADR-003: ShoppingItem как денормализованный кэш

**Дата:** 2026-10-05  
**Статус:** Принято

**Контекст:**  
Shopping List — производные данные. Можно хранить в БД или вычислять на лету.

**Решение:**  
Хранить в БД как кэш `ShoppingItem`. При изменении меню — полный пересчёт.

**Причины:**  
- Сохранение `isPurchased` между пересчётами
- Быстрый доступ без пересчёта при каждом запросе
- Простая логика восстановления состояния по ключу `(ingredientId, unit)`

**Риски:**  
- Кэш может рассинхронизироваться с меню (митигация: всегда пересчитывать при изменении MenuItem)

## ADR-004: Ужин не является отдельной сущностью

**Дата:** 2026-10-05  
**Статус:** Принято

**Контекст:**  
По требованиям ужин = обед. Нужно решить, хранить ли его отдельно.

**Решение:**  
Ужин не хранится в БД. Frontend отображает обед повторно как ужин.

**Причины:**  
- Нет дублирования данных
- Нет риска рассинхронизации обеда и ужина
- Соответствует бизнес-правилу «ужин всегда равен обеду»

## ADR-005: CookingHistory обновляется при запросе, не по cron

**Дата:** 2026-10-05  
**Статус:** Принято

**Контекст:**  
Нужно автоматически фиксировать историю приготовления. Варианты: cron-задача, обновление при запросе.

**Решение:**  
При каждом запросе `GET /menus/current` и `GET /menus/:id` проверять MenuItem с датой в прошлом без записи в CookingHistory → создавать записи.

**Причины:**  
- Нет нужды в планировщике задач
- Простота реализации
- Для семейного приложения достаточно

## ADR-006: Конверсия единиц измерения при агрегации

**Дата:** 2026-10-05  
**Статус:** Принято

**Контекст:**  
Один ингредиент может быть добавлен в разных блюдах в разных единицах (мл и л, г и кг).

**Решение:**  
В domain layer хранить таблицу конверсий для совместимых единиц:
- мл ↔ л (1000 мл = 1 л)
- г ↔ кг (1000 г = 1 кг)

При агрегации нормализовать к меньшей единице (мл, г), при отображении — конвертировать если >= 1000.

`PIECE` и другие несовместимые единицы — хранить отдельными строками в `ShoppingItem`.

## ADR-007: Settings хранятся в БД

**Дата:** 2026-10-05  
**Статус:** Принято

**Контекст:**  
Настройки (размер семьи, сложность по дням) могут быть захардкожены или храниться в БД.

**Решение:**

- Не нужны перезапуски при изменении

## ADR-009: Нормализация единиц измерения к базовым при агрегации

**Дата:** 2026-10-05  
**Статус:** Принято

**Контекст:**  
Один ингредиент может быть добавлен в разных блюдах в разных единицах (мл и л, г и кг).

**Решение:**  
В domain layer (`unitNormalizer.ts`) нормализовывать к базовым единицам при агрегации:
- GRAM + KILOGRAM → базовая единица **GRAM** (1 кг = 1000 г)
- MILLILITER + LITER → базовая единица **MILLILITER** (1 л = 1000 мл)
- PIECE → без конвертации, всегда отдельно

После агрегации — форматирование для отображения:
- ≥ 1000 г → кг (1500 г = 1,5 кг)
- ≥ 1000 мл → л (1500 мл = 1,5 л)

`ShoppingItem.unit` в БД хранит базовую единицу (GRAM, MILLILITER, PIECE).

**Отклонённый вариант:** «единица определяется первым встреченным ингредиентом» — непредсказуемо и зависит от порядка.

## ADR-010: ShoppingItemDate — отдельная таблица для дат необходимости

**Дата:** 2026-10-05  
**Статус:** Принято

**Контекст:**  
ShoppingItem должен хранить даты, когда продукт нужен. Варианты: JSON-массив прямо в ShoppingItem, или отдельная таблица.

**Решение:**  
Отдельная таблица `ShoppingItemDate` (1:N к ShoppingItem):
- `ShoppingItemDate.neededAt` — DateTime конкретного дня
- Cascade delete от ShoppingItem

**Причины:**  
- Нормализованная структура, легко расширяемая
- PostgreSQL не имеет нативного типа массива DateTime с хорошей поддержкой в Prisma
- В будущем можно добавить метаданные к дате (например, приём пищи в этот день)

## ADR-011: targetServings вычисляется, не хранится

**Дата:** 2026-10-05  
**Статус:** Принято

**Контекст:**  
TargetServings = familySize × mealsPerDay. Нужно решить: хранить явно или вычислять.

**Решение:**  
Не хранить `targetServings` в БД. Вычислять в domain layer:
```ts
const targetServings = settings.familySize * settings.mealsPerDay;
```

**Причины:**  
- Устраняет возможность рассинхронизации (targetServings ≠ familySize × mealsPerDay)
- Меньше полей в БД
- Вычисление тривиально и читаемо

**Следствие:** `familySize` и `mealsPerDay` не хардкодятся в domain-функциях — всегда передаются через `settings`.

## ADR-012: Архив меню сохраняется, генерация возвращает 409 при конфликте

**Дата:** 2026-10-05  
**Статус:** Принято

**Контекст:**  
При повторной генерации нужно решить: перезаписывать или сохранять предыдущее меню.

**Решение:**  
- Старые `WeeklyMenu` не удаляются — хранятся как архив
- `POST /menus/generate` принимает `weekStart` и возвращает **409 Conflict** если меню на эту неделю уже существует
- Явная перегенерация: `POST /menus/:id/regenerate` (полностью заменяет MenuItem и пересчитывает Shopping List)

**Причины:**  
- История меню полезна для анализа CookingHistory
- Явный конфликт лучше молчаливой перезаписи
- UX: пользователь видит предупреждение перед сбросом текущего меню

## ADR-013: Генератор планирует наиболее ограниченные дни первыми

**Дата:** 2026-10-05  
**Статус:** Принято

**Контекст:**  
Если дни с жёсткими ограничениями Difficulty обрабатываются в случайном порядке, подходящие блюда могут быть «выбраны» другими днями раньше.

**Решение:**  
Перед генерацией обедов: сортировать дни по количеству доступных кандидатов (по возрастанию — наиболее ограниченные первыми):

```ts
const sortedDays = weekDays.sort((a, b) =>
  getCandidateCount(a, pool) - getCandidateCount(b, pool)
);
```

**Причины:**  
- Жёсткий детерминированный алгоритм без backtracking
- Простой и предсказуемый
- Достаточен для MVP (7 обедов, ~10-15 блюд в базе)

**Допущение:** Если даже этот порядок не помогает — генератор возвращает явную ошибку.

## ADR-014: syncCookingHistory() — отдельная сервисная функция

**Дата:** 2026-10-05  
**Статус:** Принято

**Контекст:**  
Автоматическое обновление CookingHistory нужно вызывать в нескольких местах. Если логику встроить прямо в GET /menus/current — она скрыта и не переиспользуема.

**Решение:**  
Отдельная функция `syncCookingHistory(menuId)` в `menuService.ts`:
1. Находит MenuItem с датой в прошлом без записи в CookingHistory
2. Создаёт записи CookingHistory
3. Обновляет `Dish.lastCookedAt` (кэшированное значение)

Вызывается явно из любого handler, где это уместно (GET /menus/current, GET /menus/:id).

**Важно:** `Dish.lastCookedAt` является **кэшем** — производным от последней записи CookingHistory. Единственный источник истории — таблица `CookingHistory`.
